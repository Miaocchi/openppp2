# VPN 网络生命周期合同

> Status: Active contract and implementation roadmap
> Type: Architecture
> Last verified: 2026-10-12（对照网络清理、恢复日志、桌面进程状态和现有合同测试）
>
> **用途：**定义 OpenPPP2 对操作系统网络控制面的修改、登记、验证和恢复行为。
> 本页是生命周期 Epic（GitHub Issue #82）的仓库内合同；Issue 和代码实现必须引用这里的
> 不变量。它不把尚未实现的能力描述成当前行为。

## 1. 范围和术语

网络控制面包括虚拟网卡、IPv4/IPv6 地址、路由、DNS、系统代理和防火墙规则。数据面
隧道协议不属于本合同，但连接状态只有在所需控制面事实验证成功后才能发布为已建立。

- **资源**：一个可独立修改和恢复的控制面对象（例如某个网卡的 IPv4 DNS）。
- **所有权**：本次 OpenPPP2 会话写入资源的唯一标识、目标值和会话令牌。
- **快照**：修改前的值、配置模式、稳定资源身份和存在性信息。
- **恢复记录**：持久化的预写意图和确认状态。记录未验证恢复成功前不能删除。
- **冲突**：恢复时当前值已经不是本会话确认写入的值，或目标资源身份发生变化。

## 2. 强制不变量

1. **先登记后修改。** 每次 OS 写入前必须持久化足以恢复原状的快照、目标值和所有权。
2. **资源独立收尾。** DNS、路由、代理、地址和网卡清理分别执行、验证和报告；一个资源
   失败不能跳过无关资源。
3. **验证后提交。** 只有读取 OS 实际状态确认恢复完成，才能删除对应恢复记录。
4. **比较后恢复。** 当前值仍等于本会话写入值时才允许自动写回；检测到用户或其他
   VPN 的后续修改时保留记录并报告冲突。
5. **失败可重试。** 写入、落盘、锁、恢复或验证失败必须留下可重放记录，并阻止新的
   会话覆盖未处理的资源。
6. **状态诚实。** 进程被强制终止不等于网络已恢复；桌面端必须显示
   `recovery_pending`，不能把强杀报告为干净退出。
7. **范围受限。** 默认只修改明确授权的虚拟网卡或选定物理网卡；不得按地址猜测并
   删除其他程序的路由或 DNS。
8. **并发互斥。** 同一主机上修改控制面前必须持有进程间所有权租约；租约不可用时
   fail-closed。

## 3. 生命周期状态和操作顺序

```text
IDLE -> SNAPSHOT -> APPLYING -> VERIFYING -> ESTABLISHED
                  |                    |
                  +--> ROLLING_BACK ---+
                                      |
                         verified -> IDLE
                         conflict/failure -> RECOVERY_PENDING
```

正常停止顺序为：停止新增流量，分别停止资源写入，执行 DNS、路由、代理、地址和网卡
恢复，读取并验证每项实际状态，最后发布 `stopped`。连接阶段任何已完成的 apply 失败
都必须回滚；回滚失败进入 `RECOVERY_PENDING`，而不是发布 `connected`。

Core 超时或崩溃时，桌面端只能终止 Core 并转交独立恢复路径。恢复执行器可以是常驻
服务、系统任务或下一次启动检查；普通进程不能承诺在被强杀后继续执行清理。

## 4. DNS 策略边界

当前实现和文档必须区分以下三种产品策略：

| 策略 | 默认状态 | 合同 |
|---|---|---|
| 虚拟网卡 DNS | 推荐默认 | 只写已授权虚拟网卡；物理网卡保持原配置。不能宣传为严格防泄漏。 |
| 受控接管 | 显式开启 | 只写选定网卡；保存自动/静态模式、IPv4/IPv6 列表和稳定身份；恢复前比较当前值。 |
| 严格防泄漏 | 独立能力 | 必须声明 UDP/53、TCP/53、DoT、DoH 和无法识别加密解析的支持边界；不把
  `intercept-unmatched` 描述成整个操作系统的 DNS 劫持。 |

DNS 恢复与路由恢复是两个资源集合。路由删除失败时仍必须尝试 DNS 恢复，反之亦然。
DHCP/自动 DNS 恢复必须恢复“自动模式”语义，不能把一个地址列表或 `DhcpEnabled`
字段误当成 DNS 配置。

## 6. Issue 拆分和验收门槛

Issue #82 是 Epic。子 Issue 应保持以下边界，避免再次把 Core teardown 当作恢复服务：

| 子任务 | 交付物 | 验收证据 |
|---|---|---|
| Wave 0：清理正确性（#83/#84/#85/#87） | DNS/路由/代理的独立结果、授权网卡、apply 失败回滚 | 静态合同测试；每个资源失败仍执行其他资源 |
| Wave 1：恢复事务（#83 的后续） | Snapshot、Journal、Apply、Rollback、Verify 接线 | Journal 故障注入；写后崩溃和重试；未验证记录不删除 |
| Wave 2：桌面和 Core 停止协议（#86） | 超时状态机、独立恢复入口、启动恢复门禁 | Core 强杀、桌面超时、重启后恢复；UI 不报告虚假成功 |
| Wave 3：平台策略 | Windows/Linux/macOS 适配；IPv6、DHCP、网卡切换 | 隔离网络环境对比接口、DNS 模式、地址和路由快照 |
| DNS 拦截边界 | UDP/53、TCP/53、DoT、DoH 的能力声明和测试 | 每种协议单独测试；未知加密流量不作全量承诺 |
| 共存和冲突 | 资源所有权、compare-and-restore、冲突报告 | 用户手动改 DNS、第二 VPN 改路由时不盲目覆盖 |

每个子 Issue 的完成条件必须包括：代码路径、失败路径、验证方式、平台限制和未覆盖
范围。仅函数返回成功或进程退出不能作为恢复成功证据。

## 7. CI 和平台验收矩阵

离线单元测试只能证明序列化、所有权和状态机逻辑。发布前仍需在受控环境验证：

| 场景 | 必须比较的结果 |
|---|---|
| 静态 IPv4/IPv6 DNS | 地址列表、存在性和自动/静态模式恢复 |
| DHCP DNS | 恢复为自动模式，而不是写回旧地址列表 |
| 部分网卡 down / Wi-Fi 切换 | 只处理原身份仍存在且由本会话拥有的接口 |
| 路由或 DNS 单项失败 | 其他资源继续清理，失败记录可重试 |
| Core 强杀/桌面超时 | 独立恢复组件或下次启动消费记录 |
| 用户改 DNS / 多 VPN | 冲突可见且不覆盖后续修改 |
| 正常退出 | 实际 OS 状态验证后才清除记录并报告成功 |

真实 Windows、特权 Linux namespace、移动端 VPN 框架测试不能由普通本地单元测试替代。
任何 CI 工作流若未运行这些环境，报告中必须明确列为未验证。

## 8. 配置和命名约束

方案中的 `network.mode`、`restore_on_exit`、`persistent_recovery`、`dns.mode`、
`routes.ownership_tracking` 等字段目前只是设计输入，不是已支持的公共配置。实现前
不得把示例配置复制到默认配置或文档的“可用字段”表中。`intercept-unmatched` 仅表示
已进入 TUN 且匹配现有处理路径的查询，不表示系统级 DNS 劫持。
