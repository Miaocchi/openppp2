## 目标与范围

客户端使用同一逻辑会话，同时通过 TCP 直连、WS/WSS 反代及不同 CDN 入口连接服务端，统一承载业务流量。多条路径应能并行工作，不只是轮流尝试备用地址。

第一版针对同一服务端进程的多个入口。不涉及多网卡、Wi-Fi/蜂窝聚合，也不涉及跨服务端实例共享会话。反代/CDN 的连接须最终落到同一进程；普通 HTTP CDN 入口使用其支持的 WS/WSS，不假设支持原始 TCP。

示意：客户端通过 TCP 直连、WSS → CDN A → 反代、WSS → CDN B → 反代，同时接入同一 PPP 服务端会话。

## 已有基础（需结合最新主线复核）

- `ppp/app/client/VEthernetExchanger.cpp`：传输工厂已有 TCP、WS、WSS 实现；入口解析主要复用单个 `client.server` 和缓存。
- `ppp/app/mux/vmux_net.cpp`：已有多承载连接、调度、重排、协商式可靠传输及单承载退出处理。
- `MuxConnectAllLinklayers` / `MuxGrowLinklayers`：已有初始连接和运行时扩容入口，但需核对部分路径失败时的行为。
- `ppp/app/server/VirtualEthernetNetworkTcpipConnection.cpp`：承载接入会查找会话、校验 mux 参数；需审查完整认证链，不能仅凭客户端 ID 归并连接。
- 现有 VMUX 主要承载逻辑 TCP 流；UDP、其他隧道流量及主控制连接的覆盖范围须明确，不能默认都已支持多路径。

## 期望行为

- 每条路径独立描述协议、连接地址、WS Host/path、TLS 服务名等；由方案确定字段及校验规则，兼容旧单入口配置。
- 多条健康路径可同时参与调度；优先复用现有 VMUX，说明是否及如何提供主备、自动择优和聚合策略。
- 部分入口不可达时仍能建立可用会话；失败路径独立退避、重连并重新加入，避免重连风暴。
- 单路径失败不应无条件销毁其他健康路径或重置所有业务流；明确可靠传输协商、重排及恢复能力的前提和边界。
- 主控制连接失败、全部路径中断、部分路径恢复时，有明确的会话状态机和恢复语义。
- 各入口地址及 DNS 更新需正确纳入 VPN 绕行管理，防止外层连接进入自身隧道；处理 CDN 空闲超时和连接轮换。
- 可观察每条路径的状态、RTT、收发量及重连原因；认证凭据和完整连接地址不得泄漏到日志。

## 请 Astra 输出

1. 核对当前代码和调用链，列出可复用能力、实际缺口及高风险耦合。
2. 给出配置草案、客户端/服务端改动边界、会话绑定与能力协商方案，并说明旧版本兼容和降级方式。
3. 设计路径与主控制连接的状态机、调度和故障恢复语义；区分首版范围及后续工作，明确 TCP/UDP 各自覆盖程度。
4. 排出可独立审查的阶段/PR，列出涉及模块、依赖、测试、验收条件和回退方法；不要在排方案时直接实现。

## 验证约束与验收重点

先做离线单元测试和隔离的传输/协议测试。未经用户授权，不启动 PPP 客户端，不修改路由、DNS、代理或活动连接。

验收至少覆盖混合 TCP/WS/WSS、部分入口启动失败、单路径断开与恢复、主控制连接中断、全部路径中断、明显不同 RTT、CDN 超时、错误会话接入和旧配置兼容。真实 CDN/VPN 验收单独安排，不能用启动日志代替有效业务流量证据。

本需求独立于清理 PR #151 和 RACK PR #145；新工作应从届时最新主线开展，不混入这两个 PR。
