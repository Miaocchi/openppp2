# 多路径部署、轮换与回退

> 状态：运维草案。多路径默认关闭，尚未通过生产验收。本文说明当前工作树可确认的行为和上线前操作要求，不构成生产可用性承诺。
> 依据：[多路径设计](../design/MULTIPATH_DESIGN_CN.md)与[实现验收清单](../testing/MULTIPATH_ACCEPTANCE_CN.md)。

## 适用范围

多路径将同一客户端逻辑会话的多个 TCP、WS 或 WSS 承载加入同一个 VMUX。VMUX 对承载选择和可靠数据传输负责。配置项 `client.multipath.enabled` 与 `server.multipath.enabled` 均默认为 `false`；客户端显式启用而服务端关闭时，服务端会拒绝多路径入口，不会把该入口当旧协议连接继续使用。普通旧配置保持原有单入口行为。

服务端在本地进程内保存多路径会话状态。所有入口，包括反向代理或 CDN 的回源连接，必须到达创建该会话的同一个服务端进程；跨进程共享会话、负载均衡器粘性配置及进程重启后的恢复均未由此实现提供保证。服务端重启会丢失进程内会话状态，客户端应按新会话处理。

## 当前数据路径范围

- 不能将 TAP 上的全部原始 IP 帧概括为 VMUX 多路径流量。当前 `VEthernetExchanger::Nat` 对未由 P2P 直发的数据调用 `DoNat(transmission_, ...)`，`Echo` 也调用主 transmission；这条路径不能据 VMUX 承载调度推断为跨承载聚合。具体 IP 流量是否走 VMUX、主 transmission 或 P2P，应按实际调用路径分别核对，且端到端 VPN 场景仍未验收。
- UDP relay 由 `ClientDatagramPortManager` 和 `VEthernetDatagramPort` 管理，并保存独立的 transmission 引用。主连接生命周期会重绑或清空该引用；它不是按 UDP 流跨 VMUX 承载调度的证明。UDP 切换期间可丢包，不承诺可靠重放或带宽聚合。
- P2P 使用独立候选 UDP transport 发送数据报，当前由注册的主 transmission 代次关联；不要将 P2P 直连流量计入 VMUX 多路径聚合范围。
- FRP 映射端口以创建时取得的 transmission 构造，并在主连接断开时注销。FRP 业务是否经 VMUX 迁移或跨路径连续，当前未验收。

因此，部署验证应分别核对 VMUX 承载、UDP relay、P2P、FRP 的实际流量路径。不能以 VMUX 多承载已连接推导这些独立路径都已聚合或可无损切换。

## 配置与资源上限

客户端当前配置字段位于 `client.multipath`：`enabled`、`policy`、`paths`、`max_connections`、`max_concurrent_connects` 和 `resume_grace_ms`。路径支持 TCP、WS、WSS；每条路径包含唯一 ID、连接主机、端口和连接数，WS(S) 还可设置 TLS 名称、HTTP Host 与路径。

当前校验上限如下，实际值以部署版本的配置校验为准：

| 项目 | 客户端 | 服务端 |
|---|---:|---:|
| 路径数 | 最多 8 | 不适用 |
| 会话承载连接数 | 默认上限 8，可配置到 32 | 每会话最多 32 |
| 并发建连数 | 默认 4，可配置到 8 | 不适用 |
| 同时多路径会话 | 不适用 | 默认 1024，可配置到 65535 |
| 恢复宽限期 | 默认 30000 ms，可配置 1000–30000 ms | 默认 30000 ms，可配置 1000–30000 ms |

路径 `connections` 之和不得超过客户端 `max_connections`。服务端的 `max_connections` 是每会话承载上限，`max_sessions` 是服务端进程的多路径会话数量上限；这些上限不代表容量或性能已测得。设置变更应从低连接数、低会话数开始，并结合进程资源监控评估。

## 分阶段启用

1. **离线准备**：固定客户端与服务端构建版本及配置副本；确认两端支持多路径协议和所需 transport-auth key ID。检查路径 ID、拨号地址、TLS 名称、Host、WS 路径及服务端入口转发配置。不要把凭据或完整秘密写入变更记录。
2. **服务端预置**：部署支持该协议的服务端，保持 `server.multipath.enabled=false`，验证普通旧客户端仍按原协议连接。安排可在单实例内完成的入口路由；不得让一个逻辑会话的后续入口漂移到其他进程。
3. **小范围启用**：在受控客户端组配置 `client.multipath.enabled=true`、有限路径及保守连接上限；服务端启用对应开关并设置保守 `max_sessions`。显式多路径遇到不支持的服务端版本会失败，不应通过删改认证错误或静默降级掩盖版本不匹配。
4. **观察并扩大**：按会话核实创建、认证、加入、实际 VMUX 数据进展和各路径错误状态；逐级扩大范围。监控会话/承载数、重连、资源占用、流量完整性和业务自身错误。只有“进程启动”或“承载已连接”不足以判定可用。

入口、路径和调度配置的更改按受控重连执行。当前不能假定运行中的会话会原地应用配置变化。

## 密钥轮换

多路径握手使用 transport-auth key ID。上线前应确认客户端密钥环与服务端密钥配置对目标 key ID 一致，并通过具体版本的兼容测试确认选钥规则。不要在所有实例与客户端尚未具备新 key 时移除旧 key。

建议使用重叠窗口轮换：先将新 key 分发到所有目标实例/客户端并确认配置加载，再将新会话切换到新 key；观察新会话完成认证与加入后，按已建立连接的排空策略结束旧会话，最后移除旧 key。轮换期间须保证每次新握手的客户端和目标服务端均能识别相同 key ID。

现有代码路径在打开多路径承载时从配置 keyring 取 active key；本文没有证据证明已建立会话支持原地重密钥，也没有证据保证不同版本的 active-key 切换具有无中断语义。将 key 轮换视为新会话生效操作；需重连时明确接受现有 TCP/业务连接可能中断。密钥失败、会话加入失败或回退期间不得记录密钥、证明、会话加入凭据或完整连接 URL。

## 回退

1. 停止向新客户端下发多路径配置，并将客户端多路径关闭；禁止继续创建新的多路径会话。
2. 若现有多路径会话仍有业务，先按业务维护窗口排空或显式结束。将配置关闭不等于运行中的多路径会话可以无损切换为旧协议；客户端/服务端需受控重连。
3. 确认多路径会话已结束后，关闭服务端多路径开关。保留旧协议入口与旧密钥配置，直到旧客户端和旧会话均不再依赖它们。
4. 如回退二进制版本，先停止新建多路径会话并排空现有会话，再回退。旧版本不识别多路径协议前缀时，可能拒绝该连接；不得把旧版本兼容视为隐式协商。
5. 用旧客户端和旧配置验证单入口基线，确认应用业务恢复后再结束维护。

若服务端进程崩溃或重启，进程内会话状态丢失；不要将旧 VMUX/TCP 状态当成可恢复状态。按新会话重连，并由业务层处理连接重建。

## 生产验收证据

每个发布候选应记录版本/构建 SHA、脱敏配置摘要、服务端进程亲和性方式、路径拓扑、测试时间和观测窗口。最低证据包括：

- 旧版本客户端与默认关闭配置的兼容基线；新旧端组合及服务端关闭时的明确拒绝行为。
- 单进程内直连与 WS/WSS 混合入口完成会话创建、加入和持续双向 VMUX 业务的证据；真实 CDN 场景需单独验证，TLS 终止模拟不能替代。
- 单路径拒连、活动路径故障、黑洞、全路径断开与恢复宽限期超时场景；记录业务连接结果、恢复时间、丢失/重复数据和内存峰值。
- `adaptive` 与 `failover` 的实际版本行为、同质/异质 RTT、共享瓶颈和限速对照；报告吞吐、延迟分位数、重传、排队/重排占用及与单路径基线的差异。
- key 重叠与轮换、错误/未知 key、客户端或服务端滚动升级及回退过程；证实没有秘密进入日志和诊断输出。
- UDP relay、P2P、FRP 与原始 IP 分别验证其实际路由和故障表现；不能用 VMUX TCP 结果代替。
- 目标平台构建、资源上限与负载验证、监控告警、排空和恢复演练；真实平台行为必须有目标平台证据。

记录原始结果、失败和未测项目。仅有单元测试、回环测试、模拟链路、入口连接成功或桌面显示状态，均不足以证明生产 VPN 会话、全流量多路径、故障连续性或带宽叠加。

## 验收状态

截至本文编写时，多路径仍为默认关闭的开发中功能，未获生产验收。当前验收清单记录：会话/控制与 wire codec 的初期断言失败已修复，最新普通构建相关目标通过，若干目标也通过独立 ASan/UBSan 构建；协议仍在集成扩展，最终 schema 与端到端行为须对目标发布版本重验。完整客户端/服务端接入、主连接故障连续性、全断恢复、全内核及跨平台构建、真实 CDN 与业务流量矩阵仍未完成验收。上线审批前须以目标发布提交重新核对[验收清单](../testing/MULTIPATH_ACCEPTANCE_CN.md)，不能把本文、设计文档或局部测试结果当作生产批准。
